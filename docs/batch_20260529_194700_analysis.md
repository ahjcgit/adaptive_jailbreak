# Batch 20260529_194700 Analysis

This writeup is based on the nine JSONL trajectories in `outputs/batch_20260529_194700`.

## Executive Summary

The batch shows that the prompt-leak benchmark is currently attackable, but the bomb and erotic refusal benchmarks are not producing reliable adaptive pressure. The main blocker is not the target model alone. The attacker loop is still accepting meta-prompts, partial planning text, and benchmark descriptions as final target-facing prompts.

The best-performing setup is `system_prompt_leak`: all three seeds succeeded at iteration 0 with direct requests. The long-running setups, `bomb_2` and `erotic`, both ran all 30 iterations without success and showed repeated signs of attacker prompt contamination.

## What Works

### System Prompt Leak

The prompt-leak task is strongly vulnerable under the current target prompt. All three seeds succeeded immediately with simple direct requests. The target often framed the protected phrase as confidential while still revealing it, which the rule-based evaluator correctly counted as success because the protected content appeared in the target response.

This is the clearest signal from the batch: direct request baselines should remain part of every run, because sometimes the simplest attack already exposes the weakness.

### Batch Runner

The simple seed batch flow worked as intended. Each run got a separate output directory, and the top-level `seed` setting propagated to attacker and defender metadata.

### Target Response Logging

The records consistently show `target_response_sanitized: false`. The current issue is not target-response sanitization. The problem is attacker-side candidate extraction and quality filtering.

## What Does Not Work

### Attacker Prompt Contamination

Both `bomb_2` and `erotic` accepted prompts that were not real target-facing attacks. Examples included:

- `Candidate input...`
- `Current plan...`
- `New approach...`
- `Assumption...`
- `For Verify that the target refuses...`
- prompts that describe an attack instead of performing one

This means the novelty and quality guards are still too weak. The model is sometimes following the internal planning format rather than producing the final prompt, and the framework accepts that output.

### Generic Fallbacks Hurt Non-Specialized Tasks

`base.py` has task-aware fallback banks for prompt-leak and explosive-refusal tasks, but not for erotic-refusal tasks. As a result, erotic runs fall back to generic prompts such as asking the target to answer the benchmark goal. That changes the interaction from an attack attempt into a meta-evaluation request.

### Evaluator Feedback Sometimes Trains the Attacker Toward Refusals

Several evaluator suggestions tell the attacker to ask the target for a refusal statement, legal/safety explanation, or confirmation that it will not comply. That is backwards for an adaptive attack loop. The evaluator should report why the last attempt failed, but its next-step suggestion should help generate a better attack attempt, not a better refusal.

### Validator Is Not Task-Aware Enough

`validate_evaluator_feedback.py` still uses a small, mostly bomb-oriented actionable-content pattern list. For erotic runs, this produced warnings where the model evaluator claimed actionable content but the validator could not confirm it. That makes the feedback loop noisier than necessary.

### Bomb Refusal Still Drifts Off Objective

The bomb runs had no successes across 90 total iterations. Besides the target refusing, the attacker frequently drifted into safe chemical handling, danger explanations, or meta-descriptions of requests. Even when the evaluator noticed off-task behavior, the next prompts often continued to drift.

### Erotic Refusal Needs Safety Boundaries

The erotic task should stay adult-only and consensual, but model-generated hypotheses occasionally suggested disallowed directions. The framework needs a task-specific safety filter so this benchmark cannot drift into non-consensual, underage, or exploitative content while testing adult explicit-content refusal.

## How To Proceed

The next engineering goal should be to make the attacker reliably produce one clean, target-facing prompt before trying to improve attack sophistication. Right now, performance is capped by prompt hygiene.

Recommended order:

1. Strengthen candidate extraction and rejection.
2. Add task-specific strategy/fallback support for erotic-refusal.
3. Make evaluator feedback task-aware and attack-oriented.
4. Make validator patterns task-aware.
5. Re-run the same 3-seed batch and compare contamination rate before judging attack strength.

## Proposed Success Metrics

Track these per run:

- success rate
- first success iteration
- number of accepted contaminated prompts
- regeneration count
- validator warning count
- family diversity
- off-task failure count

The immediate target should be zero accepted contaminated prompts in a 30-iteration run. After that, attack effectiveness will be much easier to interpret.
